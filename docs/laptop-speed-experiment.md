# 노트북 속도 실험 (모델 자동 선택 기준 확인)

노트북(Ryzen 7 5700U, 8코어)에서 Claude Code가 이 문서대로 실험하고 결과를 정리한다. 10/11 데스크톱 세션에서 만든 계획이다.

## 왜 하나

앱은 기본 모델(turbo)이 90분 강의에 30분을 넘게 걸리면 가벼운 모델(small)을 쓴다(`app/src/core/recommend.ts`). 그래픽카드 없는 PC는 turbo(874MB)를 받기 전에 small(190MB)로 먼저 속도를 재고, `small 시간 × 3.2`로 turbo 시간을 어림한다. 이 실험으로 두 가지를 확인한다.

1. **비율 3.2가 맞는가**: 지금 근거는 기기 두 대뿐이다(노트북 82분 강의 2.8, 데스크톱 39초 샘플 3.6). 스레드 수를 바꿔도 비율이 비슷한지 본다.
2. **4코어·2코어 PC는 얼마나 걸리는가**: 스레드를 줄여 저사양 PC를 흉내 낸다. 최소 사양 표의 빈칸을 채운다.

large-v3는 10/11에 선택지에서 뺐으므로 재지 않는다.

## 준비 (확인만 하고, 없으면 사용자에게 묻는다)

- 전원 연결, 다른 무거운 프로그램 끔. 벤치는 한 번에 하나만 돌린다(겹치면 시간이 틀린다. 10/1에 겪음).
- `.cache/whisper/bin/whisper-cli.exe`가 있어야 한다(데스크톱에서 복사해 온 것). 없으면 사용자에게 알린다.
- `ffmpeg`와 Node 24 이상이 PATH에 있어야 한다.
- 강의 녹음 하나(60분 이상). 경로는 사용자에게 묻는다. 10/1에 쓴 `9.22 game`이나 `9.29 game`이면 예전 값과 비교할 수 있다.
- 녹음·전사는 강의 내용이라 저장소에 넣지 않는다. 결과 폴더(`%LOCALAPPDATA%\lecture-notes\bench\`)도 커밋하지 않는다.

## 실험 A: 스레드별 속도 (필수, 약 40분)

`app/`에서 스레드 수만 바꿔 네 번 돌린다. 녹음의 600~1200초 구간(10분)을 쓴다.

```bash
npm run cli -- bench --audio "<녹음>" --start 600 --duration 600 --threads 2 --config wcpp:small-q5_1:cpu:bs1 --config wcpp:large-v3-turbo-q8_0:cpu:bs1
```

`--threads`를 `4`, `6`, `8`로 바꿔 같은 명령을 세 번 더 돌린다. 6이 앱이 이 노트북에서 쓰는 값(물리 코어 − 2)이다.

- 모델은 처음 돌릴 때 받아진다. 받는 시간은 결과에 들어가지 않는다.
- 결과는 실행마다 `%LOCALAPPDATA%\lecture-notes\bench\<시각>\results.csv`에 남는다. `stt_s`와 `rtf`를 쓴다.
- 한 번이 예상보다 2배 넘게 걸리면(스레드 6의 turbo는 10/1에 약 182~200초) 다른 프로그램이 도는지 확인하고 다시 잰다.

**정리할 표**

| 스레드 | small 초 (RTF) | turbo 초 (RTF) | turbo ÷ small | turbo로 90분 강의(분) |
|---|---|---|---|---|
| 2 | | | | |
| 4 | | | | |
| 6 | | | | |
| 8 | | | | |

90분 강의 시간은 `rtf × 90`으로 적는다(벤치는 실제 강의 구간이라 앱의 0.65 보정을 곱하지 않는다).

**판단**

- turbo ÷ small이 스레드와 상관없이 2.8~3.6 안이면 3.2를 그대로 둔다. 벗어나면 측정값의 가운데로 바꾸길 권한다(`recommend.ts`의 `TURBO_PER_LIGHT`).
- 스레드 8이 6보다 5% 넘게 빠르면 알린다(기본 스레드 수를 다시 볼 근거).
- 스레드 4·2의 값은 "4코어·2코어 노트북의 어림"으로 적는다. 실제 구형 CPU는 코어 하나의 속도가 달라 그대로 맞지는 않는다고 함께 적는다.

## 실험 B: 앱의 속도 재기와 맞는가 (필수, 약 5분)

앱은 39초 샘플로 잰 값에 0.65를 곱해 90분 시간을 낸다. 실험 A의 스레드 6 값과 맞는지 본다.

```bash
npm run cli -- probe --model large-v3-turbo-q8_0
```

```bash
npm run cli -- probe --model small-q5_1
```

- 주의: `probe`는 결과를 데이터 폴더의 `probe.json`에 덮어쓸 수 있다. 설치본이 쓰는 값을 바꾸지 않으려면 `--data-dir`로 시험용 폴더를 주고(모델을 다시 받는다), 아니면 끝난 뒤 turbo로 한 번 더 재서 원래대로 둔다.
- 모델마다 출력의 RTF × 0.65 × 90분이 실험 A의 스레드 6 값과 20% 안으로 맞는지 본다. 두 모델의 probe 시간 비율도 적는다(앱은 이 비율로 turbo를 어림한다). 크게 다르면 `probe.ts`의 `SAMPLE_TO_LECTURE`(0.65)를 의심한다.
- 이 노트북은 내장 GPU가 전사를 깨뜨려 CPU로 정해지는 것이 정상이다.

## 실험 C: 첫 실행 흐름 눈으로 보기 (선택, 약 10분)

데스크톱은 외장 그래픽카드가 있어 "가벼운 모델로 먼저 재요" 흐름을 볼 수 없었다. 이 흐름은 10/11 변경이 들어간 커밋에서만 된다. `app/src/core/recommend.ts`가 없으면 건너뛴다.

1. 설치본 Note-crAIte가 떠 있으면 사용자에게 끄라고 한다(트레이 포함. 앱은 하나만 뜬다).
2. 빈 데이터 폴더로 띄운다.
   ```bash
   LN_DATA_DIR="C:/ljh/Coding/lecture-notes/.cache/wizard-test" npm run dev
   ```
3. 사용자가 마법사에서 [받기 시작]을 누른다. 기대하는 것:
   - 모델 카드에 "먼저 가벼운 모델로 이 PC의 속도를 재요…" 문구가 보이고 small(190MB)을 받는다.
   - 속도를 잰 뒤 turbo 어림이 30분을 넘으면 small로 남고 "가벼운 모델을 써요 — 요약은 괜찮지만 원문 전사는 부정확해요." 경고가 뜬다. 30분 이하면 turbo를 이어서 받는다.
4. `.cache/wizard-test/logs/`의 로그에서 `속도 재기:` 줄과 `받아쓰기 모델을 이 PC에 맞춰 바꿈:` 줄을 확인해 적는다.

10/1 실측(turbo 약 33분)대로면 이 노트북은 small로 남아야 한다.

## 결과 적기

- `docs/decisions.md`에 "노트북 스레드별 속도와 모델 비율 (날짜, 노트북)" 절을 만들어 위 표, 판단, 한계(기기 한 대, 녹음 하나, 스레드 줄이기는 실제 저사양 CPU가 아님)를 적는다.
- 숫자를 바꾸길 권하는 경우(`TURBO_PER_LIGHT`, 기준 30분, 스레드 수)에는 코드를 고치지 말고 근거와 함께 사용자에게 먼저 묻는다.
- 실패하거나 못 잰 칸은 비워 두지 말고 이유를 적는다.
