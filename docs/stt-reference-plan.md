# 받아쓰기 정답 전사 계획 (10/1 세움, 10/2 정답 6개 완성·채점함)

지금까지의 받아쓰기 오류율은 "large-v3 결과와 얼마나 다른가"를 잰 것이라, large-v3보다 나아지는 변화는 좋아진 것으로 잡히지 않는다. 작성자가 데스크톱에서 전사문을 직접 들으며 고쳐 정답을 만들고, 그것으로 다시 채점한다.

**상태** (10/1 데스크톱): 아래 "정한 것"대로 정하고 도구를 만들었다. 조각 6개의 소리·시작 전사가 저장소 밖 `C:\ljh\2026-2\s3-data\정답 전사\`에 있고(`prepare.mjs`, `score.mjs`, `읽어보기.md`), 작성자가 `정답.txt` 6개를 모두 고쳤다(10/2). 채점 결과와 한계는 `docs/decisions.md`의 "받아쓰기 정답 전사 채점 (10/2)". 채점하며 알게 된 것: 시작 전사였던 조건이 그 조각에서 유리해 비교는 시작 전사가 아닌 조건끼리 해야 하고(Soniox에서 시작한 조각 3개가 turbo·large-v3·small 비교에 가장 쓸모 있었다), 정답에 편한 표기로 적은 용어(싸인·알파·데리베이션 등)를 맞추려고 `terms-extra.json`을 더했다.

## 정한 것 (10/1)

- **조각 6개**: Soniox 결과가 있는 c16·f17·g22의 10~20분, g22 40~50분(작게 말한 구간), c21 10~20분(앞 5분 반은 학생들이 문제 푸는 시간으로 보임), f17 20~30분(용어가 가장 몰린 조각, large-v3 기준 51회).
- **적는 규칙**: 3번 표대로. 다만 용어는 한글이든 영어든 편한 대로 적고 채점할 때 용어표(9/30의 `terms.json`)로 맞춘다.
- **시작 전사**: 작성자가 고치기 편한 것으로. Soniox 결과가 있는 조각은 Soniox(군말을 지우고, large-v3와 글자 단위로 맞춰 large-v3의 구간 시각을 붙임), c21·f17 20~30분은 large-v3, g22 40~50분은 앱 기본(turbo). g22 40~50분은 large-v3가 3분의 1만 받아썼다(정리 후 473자, turbo 1,148자). 시작한 전사 쪽으로 정답이 기울 수 있다는 2번의 걱정은 작성자가 들으며 정확히 고치는 것으로 받아들였다.
- **채점**: 9/30의 조건별 조각 전사(5분 조각 조건은 경계가 달라 뺌), large-v3, Soniox(3개 조각), 다듬은 전사(강의 전체 글만 남아 있어 문단 수가 맞을 때 문단 시작 시각으로 조각을 고름). 정답의 `[?]`는 그 자리에 무엇이 와도 오류로 세지 않는다. 숫자의 한글·아라비아 표기 차이는 아직 맞추지 않는다.

핵심은 세 가지다: 적는 규칙을 먼저 정하고, 강의 전체가 아니라 10분 조각 몇 개만 고치고, 받아쓰기는 다시 돌리지 않고 이미 있는 결과를 새 정답으로 다시 채점한다.

## 1. 무엇을 고칠지: 10분 조각

들으면서 고치는 일은 조각 하나(10분)에 40분~1시간쯤으로 어림한다(재 본 값 아님). 강의 전체는 무리라 조각을 고른다.

- 9/30 전사 품질 실험에서 쓴 **고정된 조각 경계 그대로** 고른다. 그래야 그때 저장된 조건별 전사를 다시 돌리지 않고 채점만 새로 할 수 있다.
- ChatKHU 받아쓰기 시험의 조각 3개(c16 컴파일러, f17 풀스택, g22 게임의 두 번째 10분)는 포함한다. Soniox 결과가 이미 있어 크레딧이 들지 않는다.
- 나머지는 **어려운 구간**에서 고른다: 작게 말한 구간(게임 강의 42~50분), 용어가 몰린 구간, 학생 질문이 섞인 구간. 쉬운 구간만 있으면 조건 간 차이가 드러나지 않는다.

## 2. 어디서 시작해 고칠지

빈 화면에서 받아 적는 것은 너무 오래 걸려 기존 전사를 고친다. 다만 시작한 전사 쪽으로 정답이 기운다(못 듣고 지나친 오류가 그 전사에 유리하게 남음).

제안: **large-v3 전사에서 시작**한다. large-v3는 노트북에서 너무 느려 앱의 후보가 아니므로, 기울어도 비교하려는 조건들(기본 모델, 다듬기, Soniox, 앞으로의 교정)에는 공평하다. Soniox 조각 3개는 Claude가 문맥만 보고 39곳을 고친 판이 있는데(`9.30 전사 품질 실험\soniox\`), 소리를 듣고 고친 것이 아니므로 그 위에서 다시 들으며 고친다.

## 3. 적는 규칙 (제안)

정해지지 않으면 채점이 흔들린다.

| 경우 | 규칙 |
|---|---|
| 군말("어", "음", "네") | 적지 않음 |
| 말을 고쳐 다시 한 부분 | 들린 대로 다 적음 |
| 영어에서 온 용어 | 한 가지로만 일관되게(한글 발음 권장). 표기 차이는 채점할 때 용어표로 흡수 |
| 숫자 | 아라비아 숫자 |
| 띄어쓰기·문장부호 | 신경 쓰지 않음(채점에서 지움) |
| 안 들리는 곳 | `[?]`로 표시, 그 구간은 채점에서 뺌 |
| 학생 발화 | 들리면 적음 |

용어 표기는 "의미만 맞으면 표기는 상관없다"는 기준(`prompt-quality-plan.md`)을 따른다. 정답에 `파서`라고 적혀 있어도 전사의 `parser`가 맞은 것으로 잡히게, 강의마다 용어표(한글 ↔ 영어)를 두고 채점 전에 양쪽을 맞춘다. 9/30 실험의 용어 목록(강의당 24~30개)이 출발점이다.

## 4. 무엇을 잴지

- **오류율**: 정답 대비, 군말·띄어쓰기·표기 차이를 지운 뒤
- **오류의 종류별 수**: 빠뜨림, 지어냄, 바꿔 적음. 복습하는 학생에게는 빠뜨림과 지어냄이 더 치명적이다.
- **용어 적중률**: 정답에 나온 전문용어 중 맞게 적힌 비율
- **잡음 폭**: 0.99배 대조군을 새 정답으로 다시 채점해, 차이를 믿을 수 있는 선을 다시 잡는다(large-v3 기준에서는 강의별 ±0.009).

## 6. 도구 (데스크톱에서 만든다)

- **준비 스크립트**: 고른 조각의 소리 파일과, 구간 시각이 붙은 시작 전사 텍스트를 한 폴더에 내놓는다. 시각을 보며 편집기에서 고친다.
- **채점 스크립트**: 3번 규칙의 정리, 용어표 적용, `[?]` 구간 제외, 오류 종류별 집계. `app/src/core/compare.ts`의 CER 계산을 넓힌다.

정답 전사·용어표·채점 결과는 강의 내용이라 저장소 밖(`s3-data`)에 둔다. 숫자와 결론만 `docs/decisions.md`에 적는다.

## 정하지 않았던 것 (10/1에 위 "정한 것"으로 정함)

- **조각 수**: 6개(약 4~6시간 어림)가 제안이다. Soniox 조각 3개만 먼저 해도 5번의 1·3·4 비교는 된다.
- **적는 규칙**: 3번 표대로 갈지. 특히 군말을 빼는 것과 용어를 한글로 적는 것.
- **어려운 조각**: 어느 강의의 어느 구간인지. 강의를 들은 작성자가 고르거나, 전사가 유난히 짧은 조각을 뽑아 후보로 삼는다.
- **시작 전사**: 2번 제안(large-v3)대로 갈지.
