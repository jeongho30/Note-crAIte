- **노트북 내장 GPU는 쓸 수 없다.** CPU보다 2~3배 느리고 전사가 깨진다("(끄덕) (끄덕)…" 반복, 깨진 글자, 글자 수 절반). 첫 실행 속도 측정은 빠른 쪽만 고르지 말고 결과가 정상인지(글자 수, 반복)도 봐야 한다.
- CPU에서 turbo-q8_0이 q5_0보다 빠른 것은 노트북에서도 같다(210초 대 257초).
- 전사문 직접 비교(노트북 turbo, 9/28): 누락은 faster-whisper 227자 대 whisper.cpp 102자지만, faster-whisper의 가장 긴 누락(30자)은 강사가 같은 말을 서너 번 되풀이한 부분을 줄인 것이고, 그다음 긴 누락 두 곳은 두 엔진이 똑같이 빠뜨렸다. 나머지 차이는 몇 글자짜리가 흩어진 것이다. 나란히 읽으면 내용은 비슷하다. 전문용어는 서로 한 번씩 이겼다(polar coordinate를 fw는 "폴라코디니티", wcpp는 "콜라 코디니터"; fw는 "외우지"를 "넣으면 돼요"로 틀림). 기준 전사도 whisper 결과라 둘 다 틀리는 용어가 있고, 이런 것은 요약의 교정 목록이 고친다.
- 따라서 **"faster-whisper는 누락이 많다"는 CER만큼 심각하지 않다.** 판단은 품질보다 속도(22분 대 32분), 배포 비용(Python 실행 파일), 타임스탬프 밀도(fw는 약 30초 단위로 묶여 정리본의 시각이 성김)로 옮겨 간다. 앞의 데스크톱 판단("강의 노트에서는 누락이 더 나쁘다")도 이 기준으로 다시 읽는다.
- greedy(`-bs 1`, 노트북 같은 구간): turbo-q8_0 182.3초(RTF 0.304, CER 0.181, 90분 약 27분), turbo-q5_0 231.2초(0.385, 0.185). 같은 세션의 기본 설정 q8_0은 210.2초(0.350, 0.184). greedy는 13% 빨라지고 품질은 그대로지만, faster-whisper turbo(145.8초)와의 차이는 1.44배에서 1.25배로 줄 뿐이다. 계산 대부분이 디코딩이 아니라 인코더라서다. 벤치 설정 끝에 `:bs1`을 붙여 잰다.
- **결정(9/28)**: whisper.cpp로 통일하고 CPU 기본은 large-v3-turbo-q8_0 + greedy(`-bs 1`, 노트북 90분 약 27분). 아래는 결정 전 추천의 근거: whisper.cpp로 통일하고 CPU 기본은 large-v3-turbo-q8_0. 90분 강의 약 32분이고 뒤에서 처리하는 앱이라 받아들일 만하다. faster-whisper는 약 22분이지만 누락이 많고, 쓰려면 Python을 STT 전용 실행 파일로 다시 묶어야 한다(설치본 크기·백신 오탐·Mac 빌드 부담이 돌아옴). 결정되면 이 절, 구현 계획 artifact의 S3 표시, CLAUDE.md의 "지금 상태"를 바꾼다.

### S2 ChatKHU 요약 실측 (9/28)

입력: 63분 컴파일러 강의(`9.21 compiler`)의 정리된 전사 약 18,300자 + 필기, 과목 "컴파일러". 크레딧은 호출 전후 `/credits/` 잔액 차이로 쟀다.

- `json_schema`(strict)는 게이트웨이를 거쳐 Gemini에서도 4회 모두 형식이 지켜졌다.
- 교정 품질: gemini-3.8-flash는 보수적이고 거의 정확하다(예: "런 터미널→non-terminal", "널러오브→nullable"). gemini-3.5-flash-lite는 40개를 채우며 "80→Parsing"(3회), 대소문자만 바꾸기 같은 오치환을 냈다. 요약 모델은 gemini-3.8-flash를 유지한다.
- 오치환 방지 규칙을 추가했다: 숫자·기호로만 된 표현과 대소문자만 다른 교정은 버리고, 영문으로 시작하거나 끝나는 표현은 단어 경계를 지킨다. flash-lite 목록에서 정확히 해로운 두 항목만 빠졌다.
- 교정 개수는 같은 입력에서 2회 모두 11개로 안정적이었다. 오히려 더 좋은 전사(large-v3)에서 37개로 많았다.

### 요약 모델 비교 2차 (9/29, 데스크톱)

1차는 강의 1개, 사람이 고친 전사, 모델별 1회라 교정 품질과 편차를 볼 수 없었다. 앱이 실제로 넣는 전사로 모델 16개를 다시 쟀다(공모전 근거용).

**방법**

- 입력: 앱 기본 받아쓰기(large-v3-turbo-q8_0, greedy, 외장 GPU)를 고치지 않은 전사 4개, 과목명 함께.
  - 컴파일러 48분(필기 있음), 컴파일러 63분(필기 있음), 풀스택네트워킹서비스 167분(필기 있음), 게임프로그래밍입문 77분(필기 없음).
  - 처음 고른 63분 강의(질병)는 앱 전사가 기준 전사의 절반 길이라 뺐다. 30~40분·50~63분 구간에서 한 구간이 9분 가까이 이어지며 말이 통째로 빠졌다. 받아쓰기 쪽 문제로 따로 조사한다.
- 모델: 1K 토큰 단가가 공개된 글 모델 16개. 같은 계열의 옛 버전은 뺐다(값이 같거나 더 비쌈). 예외로 qwen3.7-max만 3.8-max보다 싸서 둘 다 넣었다.
  - 싼 모델 10개: 강의 4개 + 63분 강의로 2회 더(편차 확인).
  - 비싼 모델 6개: 63분·77분 강의에 1회씩.
  - 호출 64회, 932크레딧(남은 크레딧 1,393 → 461).

### 전사 품질 실험 (9/30, 데스크톱)

작성자 요청. 2차 비교의 강의 4개(컴파일러 48·63분, 풀스택 167분, 게임 77분). 기본은 앱 그대로(turbo-q8_0, greedy, VAD, 누락 구간 다시 받아쓰기, 설치본 LGPL ffmpeg, 외장 GPU). 조각 경계는 조건마다 같게 고정. 지표: 기준(large-v3) 대비 CER, 한글만 남긴 CER(영어 표기 차이를 뺌), 용어 적중(강의마다 24~30개 용어의 한글·영어·우리말 표기 수, 필기와 2차 교정 판정에서 뽑음), 반복 정리 수. 2차 교정 판정의 "알려진 오인식" 수는 2차 전사에서만 찾은 오류라 설정을 조금만 바꿔도 줄어(대조군도 73 → 61) 판단에서 뺐다. 전사·요약은 강의 내용이라 저장소 밖에 있다.

**잡음 기준**: 소리만 0.99배로 바꾼 대조군도 강의별 CER이 ±0.009 흔들린다.

**2A 전처리(ffmpeg 필터)**: 평균 CER 차 loudnorm +0.002, speechnorm +0.009, dynaudnorm +0.006, highpass −0.003(강의별 −0.012~+0.011), highpass+afftdn +0.021(반복 11 → 43). 잡음 수준이거나 나빠져 넣지 않는다.

**2B whisper 옵션**: `-vt 0.35` −0.003, `-vp 300` +0.004, `-vsd 300` −0.001, `-nth 0.3` 변화 없음(VAD와 함께면 쓰이지 않음), 5분 조각 −0.003(시간 1.3배), 빔 5 −0.002(시간 1.8배). 모두 잡음 수준이라 지금 설정을 둔다.

**2B `--prompt`**: `-mc 0`이면 whisper가 초기 프롬프트를 아예 쓰지 않는다(`n_max_text_ctx` 0). `--carry-initial-prompt`와 `-mc 64`·`128`로 쟀다. 과목명만 넣으면 CER +0.024~0.033으로 나빠지고, 과목명 + 필기 용어는 용어 적중이 +117~148 늘지만 CER +0.018~0.030, 한글만 CER도 0.149 → 0.154~0.168로 나빠졌다. `-mc 128`은 반복 루프가 다시 생겼다(반복 11 → 168). 넣지 않는다. 쓰게 되면 한글 프롬프트는 명령줄 인자로 넘기면 깨지므로(ANSI) 응답 파일(`@파일`, UTF-8)로 넘겨야 한다.

### 요약 프롬프트 시험 (10/1, 데스크톱)

### 필기 용어로 코드가 직접 고치기 시험 (10/2, 데스크톱)

작성자 요청. 필기에서 영어 용어(단어·2~3단어 구)를 뽑고, 전사의 한글 단어 묶음(1~3단어)의 발음 골격(자음만, 소리가 가까운 것끼리 한 무리)이 용어와 비슷하면(비슷함 기준 τ) 그 용어로 바꾸는 코드를 만들어, 필기가 있는 4개 조각(c16-1·c21-1·f17-1·f17-2)에서 앱 방식 turbo·large-v3·small에 적용해 정답으로 채점했다(크레딧 없음). 스크립트·바꾼 곳 목록은 저장소 밖 `정답 전사\notes-fix\`.

| 조건 (4개 조각) | 오류율 | 바꿈 | 지어냄 |
|---|---|---|---|
| turbo | 15.8% | 6.4 | 2.4 |
| turbo + 필기 고치기 τ=0.85 / 0.80 / 0.75 / 0.70 | 19.0 / 22.8 / 29.4 / 31.1% | 7.5 / 9.9 / 14.1 / 15.3 | 4.3 / 5.2 / 7.0 / 7.3 |
| turbo + 다듬기(luna, 같은 조각) | **13.5%** | 4.9 | 1.2 |

large-v3(14.0 → 16.8%, τ=0.85)와 small(24.4 → 25.9%)도 나빠졌다. **결론: 이 방식은 쓰지 않는다**(작성자 결정).

- turbo, τ=0.85에서 바꾼 76곳을 정답과 대조: 소리를 잘못 들은 것을 고친 곳은 6곳 안팎(파일 스트리라고 → Parse Tree라고, 오스트림 → stream 등), 이미 맞게 받아쓴 말의 표기만 영어로 바꾼 곳이 약 60곳(렉서 → lexer, 스트림 → stream, 프로토콜 → protocol: 정답은 한글인 곳이 많아 용어표에 없는 것은 오류로 잡힘), 엉뚱한 곳이 7곳("이거를 그대로 → correct로", "대기업은 갈 수 → additive increase": 발음 골격이 우연히 비슷한 한국어).
- 발음 골격 비교는 이미 맞는 음차(비슷함 1.00)와 진짜 오인식을 가르지 못한다. 기준을 느슨하게 할수록 더 나빠진다.
- 효과의 상한도 작다: turbo가 정답과 다른 곳(4개 조각 합계 약 345곳) 중 정답에 필기 용어가 든 곳은 11개이고 대부분 표기 차이다. 진짜 오인식 5~6곳을 완벽히 고쳐도 1점 안쪽이다. 다듬기는 같은 조각에서 2.3점 낮췄고 필기를 용어집으로 이미 받는다.
- 한계: 조각 4개, 영어 용어만 뽑음(한국어 용어의 오인식은 못 잡음), 용어표 밖의 표기 차이가 오류로 잡히는 채점 방식.

### whisper greedy 대 빔 서치 (10/2, 데스크톱)

작성자 요청: 정답 전사 6조각을 whisper의 greedy(`-bs 1`, 앱 기본)와 빔 서치(`-bs 5`)로 앱 방식(`WhisperCpp` + `transcribeChunks` + `clean`, 이 PC GPU 0·스레드 6, 빈 구간 다시 받아쓰기 포함)으로 받아쓰고 정답과 비교. turbo·large-v3(`large-v3-q5_0`)·small 세 모델 모두, 조건당 1회. 스크립트는 저장소 밖 `정답 전사\run-app.mjs`(`-bs5`로 끝나는 조건 이름), 결과는 `앱방식\<모델>-bs5\`.

| 정답 6조각 | greedy 오류율 (용어) | 빔 서치 5 오류율 (용어) | 차이 | 시간(6조각 합) |
|---|---|---|---|---|
| turbo | **16.2%** (72%) | 16.8% (69%) | +0.5 | 31초 → 56초 (1.8배) |
| large-v3 | 16.5% (70%) | **14.5%** (72%) | **−2.0** | 75초 → 112초 (1.5배) |
| small | 26.4% (41%) | 26.5% (48%) | +0.2 | 35초 → 68초 (1.9배) |

Soniox에서 시작해 쏠림이 없는 3개 조각만 보면 turbo 15.5 → 17.0%(+1.5), large-v3 14.3 → 12.8%(−1.5), small 24.7 → 25.6%(+0.9)이다.

- **turbo(앱 기본)는 빔 서치가 낫지 않다**: 6개 전체는 +0.5로 소음 폭 안이지만 9/30 실험(빔 5가 앱 기본보다 나쁨)과 방향이 같고 시간은 1.8배다. g22-1이 15.9 → 22.2%로 크게 나빠졌고(원인 미확인) 나머지 5개 조각은 ±1점 안팎이다. **앱 기본(turbo + greedy)은 그대로 둔다.**
- **large-v3는 빔 서치가 낫게 나왔다**(−2.0, 6조각 중 5개에서 좋아짐, g22-4는 33.7 → 24.1%). 소음 폭(1~2.5점)의 위쪽 경계라 확정은 못 한다. 노트북 CPU에서 large-v3는 이미 느려 앱 기본이 될 수 없다.
- **small**은 오류율이 거의 같고 용어 적중만 43 → 47% 정도 오른다.
- 정확도를 더 올리고 싶은 선택지를 둔다면 "large-v3 + 빔 서치"(14.5%)가 가장 낮은 오류율이지만, turbo + luna 다듬기(14.3%)와 같은 수준이고 시간 비용이 크다.
- 한계: 조각 6개, 조건당 1회, 정답 1인, GPU(이 PC) 기준이고 노트북 CPU에서는 확인하지 않았다. 시작 전사 쏠림(g22-4는 turbo에서 시작해 turbo 계열에 유리)은 앞 절과 같다.

### 요약 틀과 모델 다시 비교 (10/2, 노트북)

`docs/prompt-quality-plan.md`의 순서(채점 틀 고치기 → 분량 시험 → 모델)대로 다시 쟀다. 9/29·10/1의 점수와는 입력 전사와 채점표가 달라 이어지지 않는다(그 둘끼리도 같은 조건이 83%와 62%로 달랐다). 요약·채점·검수 파일은 강의 내용이라 저장소 밖 `s3-data\10.2 요약 비교\`에 있다(스크립트와 `README.md`, `채점 규칙.md`, `rubric.json` 포함). 이 PC에서는 whisper 받아쓰기를 하지 않아 확인용 강의는 없고, 개발용 4개(컴파일러 48·63분, 풀스택 167분, 게임 77분)로만 냈다.

**재는 방법을 먼저 고쳤다**

- 입력 고정: 9/30에 지금 앱 방식으로 받아쓴 전사(누락 구간 다시 받아쓰기 포함)와 필기·과목을 강의마다 파일 하나로 묶고 해시를 결과에 적었다.
- 채점표: 2차 채점의 항목(13/15/18/14개)을 "담았다/안 담았다"로만 답하는 사실(35/40/59/34개)로 쪼갰다. 요약을 보기 전에 만들었고, 사실마다 고정 입력에 근거가 있는지 읽어 확인했다(전부 있음). 0.5점은 없앴다.
- 채점자: 이 세션의 Claude가 아니라 채점 규칙과 가린 요약만 받은 하위 에이전트(Opus)가 채점하고, Sonnet이 겹쳐 채점했다(1단계는 전부, 2단계는 4분의 1). 강의마다 요약 약 10개씩 조각으로 나누고 조각마다 같은 기준점 요약 2개를 넣어 조각 간 잣대 차이를 쟀다.
- 채점자 일치: 사실 단위 97%, 요약별 포함률 상관 0.98~0.99, 기준점 요약의 조각 간 포함률 폭 평균 1~3%(최대 6%, Sonnet 한 조각 12%). 같은 조건 반복 간 포함률 폭은 3~11%다. 이보다 작은 차이는 구분되지 않는 것으로 본다.
- 오류 수는 1단계에서 채점자끼리 크게 갈렸다(Opus 17건, Sonnet 7건). "틀린 서술"과 "맞지만 강의에 없던 서술"을 한 칸에 세게 한 탓이라 2단계부터 두 칸으로 나눴고, 그 뒤로는 거의 겹쳤다.
- 2단계는 작성자가 갈린 곳만 검수했다: 틀린 서술 20개 중 16개 확인·3개 기각·1개는 강의에 없던 서술로 옮김, 망가뜨린 교정 20개 중 17개 확인. 두 채점자가 갈린 사실은 네 가지 기준을 정해(예: 결합 법칙은 이름만 있어도 담은 것) 요약 96개 전부에 다시 적용했고 포함률은 0~1%p만 움직였다.

**1단계: 분량(틀)** — luna 3회, flash 2회, 강의 4개, 100회, 883크레딧. JSON 실패 없음.

- grok은 요약이 짧아 포함률이 낮고 용어 병기 규칙을 거의 따르지 않았다.

- 모든 모델이 빠뜨린 내용이 있다: 풀스택 강의의 "임계값은 에러가 났던 윈도우의 절반"은 요약 22개 중 0개가 담았고, 대신 여러 모델(luna 빼고)이 강의에 없던 "Reno는 윈도우를 절반으로 줄인다"를 13개 요약에 썼다.

**한계**: 강의 4개(둘은 같은 과목), 조건당 2~3회, 채점은 Claude 계열 둘과 작성자의 부분 검수. 기준 전사가 이 PC에 없어 틀린 서술은 앱 전사·필기와 어긋나는 것만 셌다. 주제별 틀은 모양이 달라 1단계에서 안을 가릴 수 없었다(모델·회차만 가림). 용어 병기 비율은 용어표에 우리말 표기가 섞여 절대값을 믿기 어렵다.

**앱에 넣은 것**(10/2, 작성자 결정): 아래 "구현 결정" 표의 10/2 네 줄(요약 틀, 수식 되살리기, 요약 출력 상한, 추천 모델). 남은 것은 실패 유형별로 한 가지씩 고치기(모든 모델이 빠뜨린 내용, 강의에 없던 서술)와 확인용 강의 검증, 설치본에서 긴 요약이 노트·미리보기에 어떻게 보이는지 확인.

### ChatKHU 받아쓰기 시험 (10/1, 데스크톱)

ChatKHU 게이트웨이의 받아쓰기는 `stt-async-v5`(Soniox) 하나다. `POST /v1/gateway/audio/transcriptions/`(multipart, `file`·`model`·`language_hints`)로 올리면 `operation_id`가 오고 `GET …/{operation_id}/`로 결과(`text`, 화자별 `segments`의 `start_ms`·`end_ms`)를 받는다. **오디오 1분에 6크레딧**(90분 540, 올릴 때 차감·실패해도 환불 없음), 요청당 120분·25MB까지, webm은 거절.

9/30 실험의 강의 3개(c16 컴파일러, f17 풀스택, g22 게임)의 두 번째 10분 조각을 보냈다(178.35크레딧). 정답이 없어서 기준 전사(large-v3)를 Soniox 결과를 보기 전에 문맥상 확실한 오인식만 고쳐(39곳, 애매한 곳은 그대로) 기준으로 삼았다. 스크립트·전사는 저장소 밖 `9.30 전사 품질 실험\soniox\`.

| | 필러 뺀 한글 CER (c16 / f17 / g22) | large-v3가 틀린 표기를 맞힌 수 (맞는 표기 횟수, 합계) |
|---|---|---|
| 앱 기본(turbo-q8_0 greedy) | 0.139 / 0.100 / 0.170 | 25/59 |
| large-v3(고치기 전 기준) | 0.011 / 0.006 / 0.017 | 16/59 |
| Soniox | 0.121 / 0.097 / 0.171 | **48/59** |

- CER은 기준이 large-v3를 조금 고친 것이라 "large-v3와 얼마나 다른가"일 뿐이다. turbo와 Soniox가 비슷하게 나오지만 누가 맞는지는 알려 주지 않는다.
- 용어·전문어는 Soniox가 훨씬 낫다: yylex·yytext, regular expression, 트래픽, 객체지향, 시리얼 케이블, 폴라 코디네이트, 인베리언트, 좌표계 등을 처음부터 맞게 적고, 기준을 고칠 때 애매해서 둔 곳("이 입에" → "이 if에")도 맞혔다. 학생 질문도 따로 잡았다(large-v3는 교수 말로 바꿔 적음).
- Soniox는 말한 그대로 적는다: "어,", "네." 같은 필러와 되풀이가 들어간다(글자 수 +4~11%). 노트에 쓰려면 필러를 빼는 정리가 필요하다.
- 판단: 품질은 로컬보다 확실히 낫지만 90분 540크레딧(월 4000이면 약 7개)이라 기본값은 로컬 whisper로 두고, "크레딧을 써서 더 정확하게" 받아쓰는 선택지로만 검토한다.

## 엔진을 TypeScript로 (9/28)

S1 뒤에 구조를 다시 봤다. 설치본 Python 엔진의 의존성은 requests·pyyaml·psutil뿐이고(faster-whisper는 이미 벤치 전용), 하는 일은 ffmpeg·whisper-cli 실행, HTTP, 텍스트 처리였다. 모두 Node 표준 기능(`child_process`, `fetch`, `crypto`, `fs`)으로 된다. 무거운 계산은 외부 프로세스가 하므로 메인 프로세스가 막히지 않는다.

- 없어진 것: PyInstaller 묶음(26MB), stdio JSON 프로토콜과 stdout 격리, 부모 프로세스 감시, 엔진 재시작 처리, 빌드 단계 하나, 두 번째 언어·테스트 도구. Mac 빌드에서 PyInstaller를 OS별로 따로 묶을 일도 없다.
- 그대로인 것: 처리 방식과 파일 형식(10분 조각, `part_NNN.json`, whisper-cli 인자, 교정·정리 규칙), 데이터 폴더. 테스트 46개를 `node:test`로 옮겼고(47개, WAV의 LIST 청크 테스트 추가), 추가 npm 의존성은 없다.
- 이름: 구간과 조각의 필드는 TypeScript 관례대로 `startMs`/`endMs`, `startS`/`endS`로 바꿨다. 옮기기 전 저장된 작업 파일은 없다.
- 벤치의 faster-whisper 비교는 `tools/fw_transcribe.py`를 별도 프로세스로 부른다. S3에서 faster-whisper가 이겨 앱에 넣게 되면, whisper-cli처럼 따로 묶은 실행 파일을 부르는 `SttEngine`을 하나 추가한다.
- 주의: 처리 중 예외가 메인 프로세스에서 나므로 핸들러에서 잡아 화면에 넘긴다. 오래 걸리는 동기 계산(예: 90분 전사 전체 CER)은 메인 프로세스에 두지 않는다. 필요해지면 `utilityProcess`로 뺀다.
- 노트북(9/28): 앱을 띄워 화면 → IPC → 메인 → `core` 왕복과 ffmpeg 탐지를 확인했다. fw 벤치 경로도 합성 음성으로 끝까지 돌았다. whisper.cpp 경로는 whisper-cli를 복사해 온 뒤 S3에서 확인한다.

## 라이선스 검토 (9/28)

설치본에 들어가는 것 기준. 법률 자문이 아니라 각 라이선스 문서를 읽고 판단한 것이다.

- 문제없음: Electron·React·electron-vite(MIT), NSIS(zlib), whisper.cpp/ggml과 `ggml-vulkan.dll`(MIT), Whisper 모델·ggml 변환본·Silero VAD(MIT, 실행 중 다운로드), Ollama(MIT, 넣지 않음).
